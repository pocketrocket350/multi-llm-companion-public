# multi-llm-companion

複数のLLM（大規模言語モデル。文章を受け取り、回答を作るAI）を設定で切り替えられる、Windows向けの汎用デスクトップ会話アプリです。

本プロジェクトが目指す利用体験は、利用者が正規に入手し利用条件を確認した雨衣のMMDモデルとVoiSona Talkの対応ボイスを、自分のWindows PC内で接続し、文字や声で会話できる常駐型AIコンパニオンです。ご依頼でいう「GLOKコンパニオン風」とは、アバターが画面に存在し、会話・音声・表情・視線・身振りが途切れず連動する体験を指します。特定サービスの複製や公式製品化を意味しません。

公開リポジトリ自体は、特定キャラクターに依存しない汎用会話エンジンとして維持します。雨衣のMMDモデル、テクスチャ、VoiSonaのボイスライブラリ、生成音声、公式画像、公式人格設定は同梱・再配布しません。VMDは原則として`local`から読み込みますが、配布元が再配布を明示的に許可し、条件・改変の有無・必要なクレジットを個別確認したVMDは、第三者ライセンスのまま公開物へ含めます。公開する人格見本はオリジナルキャラクターのままにします。

2026-10-14現在、採用画面は9月29日、記録された10項目の日常利用は10月9日に利用者受入済みです。gpt-6-lunaとHTTP/2接続再利用を維持します。開始速度の数値目標未達とPhase 12の既知事項は、利用者が現状を了承して追加対応を終了しました。過去の不合格や制限は保持します。[フェーズ13のv1.0候補](docs/development/phase13-acceptance_ja.md)は、クリーンWindows未確認を了承した利用者により現PC検証範囲で承認済みです。今回の明示依頼により、ソース版v1.0-rc.1の公開・外部配布へ進みます。

ダウンロード先とZIPの展開・起動操作は [配布版の導入](docs/release_ja.md) を参照してください。素材と音声は同梱せず、初期状態はAPIキー不要のMock文字会話です。

完成像、現在地、今後の実装順、停止条件、完成条件は [最終設計ロードマップ](docs/roadmap_ja.md) を正本とします。

VMDを持っていない場合は、PMXを読み込んだ画面の「確認用VMDを生成して再生」から、モデル内の基本ボーンだけを使う短いオリジナル確認用VMDを生成できます。利用者が生成した確認用VMDと再配布条件を確認していない外部モーションは、公開対象外の`local`内だけに置きます。

## 現在できること

- 日本語のチャット画面で文章を送受信する
- 可能なプロバイダーでは、回答が届いた部分から順に表示する
- 設定ファイルでMock、Qwen、DeepSeek、OpenAIを切り替える
- APIを使わないMockプロバイダーで動作確認する
- キャラクター設定と会話時の行動方針を、YAML内の別項目として読み込む
- 会話履歴と、取得できた場合の入出力トークン数をSQLiteへ保存し、画面で合計を確認する
- 新しい会話を開始し、不要な会話履歴を削除する
- 接続エラーを日本語で確認する
- Voskを使い、マイク音声をPC内で日本語の文字へ変換する
- VoiSona TalkのREST APIへspeechを送り、音声として再生する
- LLMストリームで文が確定した順にVoiSona Talkへ先読み合成し、文ごとに連続再生する
- 設定画面でWhisper（高精度）とVosk（軽量）を切り替える
- 使用するマイクを選び、入力音量と認識途中の文章を確認する
- 発話後の無音を検出して自動的に録音を終了する
- 会話から役立つ情報を自動保存し、後から修正・削除し、会話への利用を停止する
- 関係の弱い記憶や重複を抑え、保存済み記憶を自然な会話の参考にする
- 回答の感情情報をなだらかに変化する会話状態として表示する
- 平滑化した一つの感情状態から、音声・PMX表情・ジェスチャー/VMD・視線・自然動作へ別々の上限付き強度を作り、適用・無効・未対応を状態表示する
- 外部画像を使わない汎用2Dアバターで、表情・視線・簡単な動作を表示する
- VoiSona Talkの状態に連動し、日本語の母音から推定した口形、手振り、うなずき、なめらかな視線移動を表示する
- PMX簡易プレビュー中でも、口形モニターで推定した母音を大きく確認する
- 待機中も呼吸・瞬き・小さな首の揺れを表示し、PMX簡易プレビューにも微小な待機動作を表示する
- VoiSona Talkの音声リクエスト状態に合わせて口パクし、音声を停止できる
- VoiSona Talkが返す音素時刻を使える場合は、文字数の推定より優先して口パクする
- 会話重視・アバター重視・顔拡大の画面表示を切り替える
- 読み上げ中に送信またはマイク入力を行うと、音声を停止して利用者の入力を優先する
- 発話開始前・再生中の割り込みで、古い音声、口形、表情、視線、ジェスチャー、非同期姿勢を同じ親世代から無効化する
- 長い会話では、保存済み履歴を消さずに古い発言を要点化して送信範囲を抑える
- 期限を過ぎた保存済み記憶は削除せず、会話の参考からだけ外す
- 3Dアバター向けに感情・動作・視線を渡す共通接続基盤を、外部通信なしのMockで確認する
- local/models/mmd 内の利用許諾を確認済みPMXモデルを、間引いた三角形面のメッシュとして簡易表示する
- PMXに設定済みの母音モーフがある場合、推定した口形を頂点変形としてメッシュへ反映する
- PMXに設定済みの表情頂点モーフがある場合、感情の強さに応じて口モーフと合成して反映する
- PMXに設定済みの目・頭・上半身ボーンがある場合、視線とうなずきを頂点ウェイトに従って反映する
- 感情、視線、ジェスチャーをPMXモデル固有のモーフ名・ボーン名・動作名へ設定で対応付ける
- キャラクター共通の表情プリセットとモデル固有のPMXモーフ名を分け、複数の表情モーフを同時に合成する
- PMXの材質モーフとUV・追加UVモーフを、頂点モーフやグループモーフと同じ表情重みへ合成する
- 標準Toon参照、スフィアの追加UV1サブテクスチャ、材質モーフのテクスチャ係数を反映し、半透明を含む全材質をPMX定義順で描画する
- PMXの呼吸・左右移動などの軽いGPU動作を約30fpsで続け、重いボーン・物理・全頂点計算を低頻度のバックグラウンド処理へ分ける
- VMDのIK有効・無効キーをPMXのIK計算へ反映し、未検出のIK名を互換性状態へ表示する
- VMDのカメラ・照明を「VMDカメラ・照明（明示再生）」選択時だけ再生し、通常表示の利用者カメラ・固定照明を維持する
- VMDとPMXの対応ボーン・モーフ・IK、未検出名、対象モデル名、最大移動量とモデル身長の比、描画未対応セクションを状態表示で確認する
- `モーションを管理`からVMDを一覧・検索・分類し、利用不可理由を確認して、本番再生と分離したプレビューと有効・無効切替を行う

標準アバターはアプリがコードで描く汎用表示です。利用者が `local` に置いたPMXモデルだけは任意で読み込めます。音声機能は初期状態で無効なので、設定なしでも文字チャットを利用できます。音声は `docs/audio_ja.md`、長期記憶は `docs/memory_ja.md`、感情状態は `docs/emotion_ja.md`、アバターは `docs/avatar_ja.md` を参照してください。

アバターの表示名、髪色、服色、リボン色は `local/avatar.yaml` で変更できます。第三者キャラクターの名称や素材パスを設定する場合は、個人利用・配信・収益化・改変など、実際の用途が許可されていることを利用者自身で確認してください。公開用の見本設定には既存キャラクター固有の情報を書きません。

## 必要なもの

- Windows 11
- Python 3.12
- インターネット接続（初回セットアップと、実際のLLM APIを使う場合）

Pythonは、インストール時に「Add python.exe to PATH」を有効にしてください。PATHとは、WindowsがPythonの場所を見つけるための設定です。

## いちばん簡単な始め方

最初はAPIキーが不要なMockで確認します。

1. [配布版の導入](docs/release_ja.md)でZIPを取得し、新しいフォルダーへ「すべて展開」します。展開先でこのプロジェクトのフォルダを開きます。
2. setup_windows.bat をダブルクリックします。
3. セットアップが成功したと表示されるまで待ちます。
4. run.bat をダブルクリックします。
5. 画面の入力欄へ文章を書き、Enterで送信します。Shift+Enterは改行です。
6. Mockから回答が表示されれば、基本動作は成功です。
7. アプリを閉じ、test.bat をダブルクリックします。
8. pytest と ruff の両方が成功したことを確認します。

setup_windows.bat は、Pythonの確認、.venv（このアプリ専用のPython環境）の作成、必要パッケージのインストール、localフォルダの作成、見本設定のコピーを行います。すでに利用者が編集したローカル設定がある場合は、内容を失わないように扱います。.envは接続先URLやモデル名などの非秘密値だけに使い、APIキーはWindowsの環境変数へ設定してください。

## フォルダの役割

- src: アプリ本体のPythonコード
- config: 公開してよい見本設定
- local: 利用者ごとのローカル設定。Gitの公開対象外
- data: SQLiteの会話データベース。データベースはGitの公開対象外
- tests: 自動テスト
- docs: 詳しい日本語資料

主な構成は次のとおりです。

    multi-llm-companion/
    ├─ src/                 アプリ本体
    ├─ config/              app、providers、persona、audio、memoryの見本
    ├─ local/               利用者用の設定
    ├─ data/                SQLiteデータベース
    ├─ tests/               自動テスト
    ├─ docs/                日本語資料
    ├─ setup_windows.bat    初回セットアップ
    ├─ download_whisper_model.bat  Whisperモデル準備
    ├─ run.bat              アプリ起動
    └─ test.bat             テストとruff

詳しい仕組みは docs/architecture_ja.md、より丁寧な操作説明は docs/beginner_guide_ja.md を参照してください。

## Mock以外のLLMを使う

Qwen、DeepSeek、OpenAIは、共通のOpenAI互換プロバイダーを通して接続します。「OpenAI互換」とは、異なるサービスを似た形式で呼び出せる仕組みです。

APIキーそのものをプロジェクト内のファイルやログへ書かないでください。設定ファイルには、値ではなく「どの環境変数から読むか」という環境変数名だけを書きます。

大まかな流れは次のとおりです。

1. config/providers.example.yaml を参考に、local/providers.yaml のプロバイダー設定を確認します。
2. 利用するサービスの公式管理画面でAPIキーを発行します。
3. APIキー、必要ならbase URLとモデル名をWindowsの環境変数へ設定します。
4. local/app.yaml のactive_providerで、使用するプロバイダー名を選びます。
5. run.bat でアプリを起動し、画面のプロバイダー名、モデル名、接続状態を確認します。

local/app.yamlにはactive_provider、providers_config_path、persona_path、database_pathを設定します。local/providers.yamlでは、providersの下に各設定名を置き、provider、base_url_env、api_key_env、model_env、temperature、max_output_tokens、timeoutを指定します。local/persona.yamlは、`character`（名前・一人称・口調・価値観など）と`behavior_policy`（回答の長さ・質問頻度・記憶利用など）を分けて持ちます。以前の`name`と`system_prompt`だけの設定も移行期間中は読み込めます。詳しくは`docs/persona_ja.md`を参照してください。

環境変数名は config/providers.example.yaml に書かれている名前と完全に一致させてください。実際のキー値を設定例へ書き込んではいけません。.env.example も変数名を案内する見本であり、実在するキーを含みません。

詳しい設定方法と一時的な環境変数の設定例は docs/providers_ja.md を参照してください。サービスごとのURL、モデル名、料金、利用条件は変わる可能性があるため、必ず各サービスの公式資料も確認してください。

## 画面で確認する場所

- 左上の時計「履歴」: 保存済み会話の選択、「新しい会話」「この履歴を削除」。削除は元に戻せません。
- 右上の歯車「設定」→「会話・音声」: 「LLM接続・マイクの設定」「記憶を管理」「人格を編集」。
- 「設定」→「表示」: アバター、カメラ、表示の操作。
- 「設定」→「診断情報」: Provider、モデル、接続状態、感情、トークン使用量。料金の表示ではありません。
- 下部の入力欄と三角矢印「送信」: Enterで送信、Shift+Enterで改行。
- 処理中だけ表示される「検索・返答を取消」「音声・動作を停止」: 対象処理の停止。

最新の画面操作は [画面ガイド](docs/development/phase11-user-check_ja.md) を参照してください。初回導入は [初心者ガイド](docs/beginner_guide_ja.md)、設定・履歴・記憶の復旧は [バックアップと復旧](docs/backup_and_recovery_ja.md)、候補の範囲と制限は [v1.0候補の導入](docs/v1_candidate_ja.md) を使います。

## 会話データと秘密情報

会話履歴は、通常はdataフォルダ内のSQLiteデータベースへ保存されます。SQLiteとは、1つのファイルで扱える小型データベースです。会話には個人情報や秘密を書かないでください。外部LLMを使う場合、送信内容は選択したAPIサービスへ送られます。

会話から保存した記憶は、関係する話題でAPIへ送られます。内容の変更や削除は「記憶を管理」から行えます。詳細は `docs/memory_ja.md` を確認してください。

APIキーは次の場所へ残さないでください。

- Pythonコード
- YAMLなどの設定ファイル
- READMEや画面写真
- テストデータ
- ログ
- Gitのコミット

もし公開場所へAPIキーを載せた可能性がある場合は、ファイルを消すだけでは不十分です。すぐに提供元でそのキーを無効化し、新しいキーへ交換してください。

## よくあるトラブル

### 「Pythonが見つかりません」と表示される

Python 3.12をインストールし、インストーラーの「Add python.exe to PATH」を有効にします。その後、新しく開いたプロジェクトフォルダから setup_windows.bat をもう一度実行してください。

### セットアップでパッケージのインストールに失敗する

インターネット接続を確認してください。会社や学校のネットワークでは、プロキシやセキュリティ設定で通信が止められる場合があります。表示されたエラーを省略せずに控えてください。

### run.bat を押しても画面が出ない

先に setup_windows.bat が最後まで成功したか確認します。localフォルダの設定ファイルが不足している場合は、見本ファイルと比較してください。コマンド画面に日本語のエラーが表示された場合は、その文章も確認してください。

### Mockでは動くが外部LLMへ接続できない

プロバイダー名、環境変数名、モデル名、base URLを確認します。APIキーの値をエラー報告へ貼らないでください。契約状態、利用上限、対象モデルを利用できるかも、サービスの公式管理画面で確認してください。

### 会話履歴を保存できない

dataフォルダに書き込みできるか、データベースを別のアプリで開いたままにしていないか確認します。データベースを手作業で削除・移動する前に、必要ならバックアップを取ってください。

### テストが失敗する

test.bat の表示を最初から最後まで確認します。pytest は動作を確認するテスト、ruff はコードの書き方や単純な間違いを確認する道具です。失敗したまま「完成」と判断しないでください。

## v1.0最終設計ロードマップ

完成像、現在位置、残工程、受入条件は [製品ロードマップ](docs/roadmap_ja.md) を正本とします。2026-10-14現在、フェーズ13は合意した現PC検証範囲で完了です。クリーンWindows未確認は制限として保持し、今回の明示依頼により、ソース版v1.0候補の公開・外部配布へ進みます。以下の旧段階の確認待ち・旧画面名は当時の技術履歴であり、9月29日・10月9日の限定受入と10月10日の速度現状了承を取り消しません。

以下は完成済み機能の技術記録です。将来の実装順や完成条件を判断するときは、段階番号ではなく最終設計ロードマップのフェーズを使用します。

### 第17段階: 表情モーフをPMXへ反映する

- 状態: 実装済み。
- 目的: LLMの `emotion` と `emotion_intensity` を、PMXモデルの笑顔・悲しみ・怒り・照れ・驚きなどの頂点モーフ、または頂点モーフへ展開できるグループモーフへ反映する。
- 実装: PMX内の頂点モーフ候補を読み取り、`local/avatar.yaml` の対応表から選ぶ。口モーフと表情モーフが同時に動いても頂点変形を失わないよう、複数モーフの差分を合成する。
- 画面: 現在適用中の表情名と強さを表示し、設定不足は日本語で案内する。
- 完了条件: 感情ごとのモーフを手動テストでき、口パク中も表情が保持され、未設定モデルでは従来表示へ安全に戻る。

### 第18段階: ボーン姿勢と視線をPMXへ反映する

- 状態: 実装済み。
- 目的: 頭、上半身、両目などのボーンを使い、視線とうなずきを実際のモデルへ反映する。
- 実装: PMXのボーン階層、親子関係、初期位置、BDEF/SDEFの基本ウェイトを読み取り、ローカル座標から画面上の頂点位置を計算する。モデル差は `gaze_bones` と `pose_bones` の対応表で吸収する。
- 安全策: 視線・うなずきの回転角度を小さく制限し、不正な親番号と循環参照では基本姿勢へ安全に戻る。存在しない設定名は画面へ日本語で表示する。
- 完了条件: 正面、左右、上下の視線とうなずきを確認でき、存在しないボーン名でもアプリが終了しない。

### 第19段階: テクスチャ付き3D描画へ移行する

- 状態: 実装済み。
- 実装: PMXのUV座標、材質の基本色、テクスチャ参照を読み込み、OpenGLを利用できるPCでは全三角形をGPUで描きます。OpenGLが利用できない場合は、間引いた単色・テクスチャ簡易表示へ安全に戻ります。追加の描画ライブラリや外部素材は使いません。
- 操作: プレビューをドラッグすると回転、マウスホイールで拡大縮小できます。「カメラを正面へ戻す」で標準の正面画角に戻ります。
- 制限: 物理演算、IK、透過材質、スフィアマップ、Toon材質などのPMX固有表現は未実装です。モデルとテクスチャは `local` 内にのみ置き、公開リポジトリへ追加しません。

### 第20段階: VTuber風の常時動作と動作合成

- 状態: 実装済み（基本動作）。
- 実装: GPU表示では、待機中に小さな呼吸、重心移動、首振りを連続して重ねます。「動きを表示」をオフにすると、待機動作を停止します。

### 第30段階: 軽いGPU動作と重いボーン・物理計算の分離

- 状態: 実装済み。自然な待機姿勢、胸郭呼吸、首、重心、まばたき、会話状態別動作、10分間の非周期性を実PMXで利用者が確認済みです。

- 非周期性: 呼吸周期、首の目標角、重心、まばたき間隔を固定正弦波ではなく、範囲内のランダムな目標と時間を滑らかにつなぎます。感情の種類と強さで振幅を小さな範囲内だけ変えます。
- まばたき: 1秒周期の全メッシュ計算から分離し、口パクと同じ顔材質の差分更新を使います。口・表情・まばたきは同じ基準姿勢へ合成するため、まばたきで口形を解除しません。
- 重い処理: VMD、ボーン、IK、物理、全頂点の再構築は約66ミリ秒周期（約15fps）へ分け、実経過時間を使って画面スレッド外で実行します。変わらない材質・法線・UV・頂点参照はモデル読込時に一度だけ準備し、ボーン変形と面展開はNumPyで一括計算します。発話中も会話ジェスチャーを含む姿勢へ衣装物理を追従させます。終了時に休止中の時間をまとめて追いつかせず、会話姿勢から待機姿勢へ複数フレームで戻します。
- 実測: 雨衣PMX（59,854頂点・98,349面）と外部待機VMDで、旧実装は1回平均757.0ミリ秒（実効上限約1.32fps）でした。高速化の試作ではNumPy一括変形が約31.2ミリ秒、事前準備済みの面展開が約6.7ミリ秒でした。実装後の一連の処理は平均49.9ミリ秒（実効上限約20.1fps）で、66ミリ秒周期を処理時間が超えない余裕を確保しています（2026年7月27日計測）。
- 完了条件: 発話中も呼吸・左右移動が止まらず、口パクと音声が第29段階より劣化せず、発話終了時にモデル位置が上下へ飛ばず、「動きを表示」をオフにすると軽い動作と重い動作の両方が止まることを確認します。
- 中止条件: 音声の乱れ、口パク開始の遅れ、発話終了時の座標飛び、画面の長い停止が一つでも再発した場合は完成扱いにせず、軽量更新・重い計算・GPU反映の各時刻を測定します。
- 自然動作の確認結果: 実画面で、待機姿勢、重心移動、浮遊に見えない呼吸、首を支点にしたうなずき、各会話状態の切替、10分間の非周期性を確認済みです。
- 自然動作の完成条件: 呼吸が上下浮遊に見えず、うなずきが腰中心の揺れに見えず、10分間見ても同じ周期が目立たず、会話状態に応じて動作が切り替わることです。これらは処理分離に成功しただけでは完了扱いにしません。

### 第31段階: 動作ミキサー

- 状態: 実装済み。音声開始前の手振り姿勢、発話中の手振り・視線・口パクの同時保持、終了時解除、割り込み、姿勢飛びがないことを実PMXで利用者が確認済みです。
- 目的: 待機、口パク、表情、視線、会話ジェスチャー、VMD、物理演算を同時に使っても、互いの結果を消したり同じボーンを暴れさせたりしないよう、一つの部品で優先順位を解決します。
- 優先順位: 緊急停止、利用者の割り込み、口パク、表情、視線、会話ジェスチャー、待機・VMD、物理演算の順です。口パクは音声再生時計に同期する高速経路が所有し、重い姿勢計算から上書きしません。
- 安全な切替: 新しい発言では古い会話ジェスチャーを解除します。すでに計算中だった古いPMX姿勢は世代番号が一致しないため画面へ反映されません。姿勢と表情は現在値から新しい目標へ補間し、一度に飛ばしません。
- 同一ボーン: 複数の動作が同じボーンを要求した場合、優先度の高い一つだけを採用します。回転角と移動量にも安全上限を設けます。異なるボーンを使う手振りと視線は同時に保持します。
- 会話動作の寿命: LLM回答の保存中には音声を開始しません。画面が最新の姿勢番号をGPUへ反映したことを確認してからVoiSonaへ一度だけ依頼し、発話中だけ会話ジェスチャーを更新します。音声終了・停止・新しい入力のいずれでもジェスチャーと視線を解除します。
- 視線ボーン: 雨衣PMXの`両目`は頂点を直接持たない中継ボーンです。現在の簡易ボーン処理では中継機能を再現しないため、実際に頂点へ影響する`左目`と`右目`へ同じ視線回転を配ります。
- 完了条件: 手振り中も口パクと視線が動き、新しい発言で古い動作を安全に中断でき、切替時に姿勢が飛ばず、同じボーンへ複数命令が重なっても不自然に暴れないことを確認します。
- 完成判定: 自動テストだけでは完成にしません。権利確認済みの実PMXで手振り姿勢への移行と姿勢切替を利用者が確認する必要があります。

### 第32段階: 3D描画品質

- 状態: 実装済み。第32段階時点の自動テスト、雨衣PMXを使ったローカルGPU診断、`SSAA 1.5x`の実画面表示を利用者が確認済みです。第41段階の比較結果に基づき現在の標準SSAAは2倍です。
- 材質: PMXの基本テクスチャ、拡散色、環境光、鏡面反射、スフィアマップ、Toon、両面表示を維持します。髪や表情を含む全材質をPMX定義順で描き、透明画素はシェーダーで破棄または合成しながら深度を書き込みます。
- 輪郭: PMX材質の輪郭フラグ、RGBA、太さと頂点ごとのエッジ倍率を読み取り、低品質以外ではSSAA内部倍率とカメラ投影後のモデル寸法に合わせて背面を外側へ広げます。近景では細線を複数の内部画素で描いて縮小し、遠景では線を弱くするため、固定ピクセル幅で起きていた近景のジャギーと遠景の太線を分けて抑えます。作者の半透明RGBAは背景色へ事前合成せずそのままGPUへ渡します。浮動小数の幅と整数の描画モードは型に対応したOpenGL APIでGPUへ渡します。`*_back`という専用裏材質がある部位では、内側へ黒い輪郭面が露出しないよう表材質の裏面と内側輪郭を描きません。
- 平滑化: `render_quality`は`low`、`standard`、`high`です。MSAAが利用できる場合は4倍・8倍を使います。このPCのようにMSAAが0倍になる環境では、標準・高品質とも2倍の内部画面をGPUで描いてから縮小します。CPUへ画像を読み戻さないため、音声・口パク経路を止めません。
- 負荷制限: 内部画面は最大辺4,096画素・最大1,600万画素に制限し、大画面では倍率を安全に下げます。同じ画像を使う複数材質は1個のGPUテクスチャを共有します。
- 状態表示: 3D状態欄へ、設定品質と実際に使えた`MSAA`または`SSAA`倍率を表示します。`SSAA`は、大きく描いて縮小することで輪郭を滑らかにする方式です。
- 制限: 現在も本格MMDランタイムではありません。第42段階のVMDカメラは透視投影だけをDense GPU表示へ安全に対応し、照明も同じ明示表示だけで使います。セルフ影、モデル表示切替、平行投影カメラ、MMD互換物理の完全再現は未対応です。

- 調査結果: VMDボーンフレームには64バイトの補間情報がありますが、従来版はこれを読み捨て、XYZ移動と回転をすべて同じ線形割合で混ぜていました。登録済みの待機VMDでは、656キーフレーム中に1,359個の非線形チャンネルがあり、配布者が設定した加速・減速が失われていました。
- 補間曲線: 各キーフレームからX・Y・Z・回転の4本のベジェ曲線を読み、移動軸ごとに別の進み方を適用します。旧版が生成した補間ゼロの確認用VMDは、互換性のため線形として読みます。
- 回転: クォータニオン4成分の単純な数値混合をやめ、同じ姿勢へ遠回りせず回転する球面補間へ変更しました。VMDの回転曲線は、この球面補間の進行割合へ適用します。
- 状態表示: 3Dモデル上の状態ラベルを廃止しました。口形と表情は既存の「アバター」ヘッダーへ表示し、顔・口・眉を隠しません。3D表示の高さは削っていません。
- 処理時間: 権利確認済みの`idle_bonyari_wide`で1,000回更新した実測は約886ミリ秒、1回約0.886ミリ秒でした。重い更新周期66ミリ秒を超えていません。
- 今回の境界: 補間と回転精度だけを原因調査に基づく最小単位として実装しました。IK、衝突物理、材質モーフ、VMDカメラを同時変更していません。
- 音声回帰対策: Windows音声機器へ発話本文を送る前に120ミリ秒の無音を置き、口パクはその無音を除いた実再生位置へ同期します。別の再生方式や二重再生は追加していません。
- 利用者確認: 「テスト」を3回送信し、毎回「モック応答です」の最初の「モ」から聞こえ、口パクが音声の最初から始まり終了とほぼ同時に閉じ、表情・まばたき・常時動作・VMDに停止や姿勢飛びがないことを確認済みです。

- 性能: 2000ボーンキー＋500表情キーの人工VMDで、読込20回平均は7.415 msから8.072 ms、5000回の1更新平均は40.412 µsから39.110 µs、ループ/切替ミキサーは12.694 µsから11.317 µsでした。拡張キーを含むループ境界は平均29.907 µs・95パーセンタイル43.895 µs、モーション切替は平均19.404 µsで、33 ms周期内です。

## 口パク障害の総括と再発防止（2026年7月）

第29段階の口パク障害では、利用者が早い時点で「3Dの動きがカクつく」と報告していました。しかし、その報告を口パク停止の原因候補として全く検討せず、「動きの精度上げは今後」と別問題にして診断対象から外しました。その後、実際のVoiSona応答、UI反映時刻、3D描画時間を測定する前に、開始条件や再生方法を推測で変更し、同じ系統の確認を繰り返しました。利用者報告では、この迷走により週次Codexトークン枠の約70%を消費しました。

最初の診断では、次の事実が確認されました。

- VoiSonaは約3.8秒間、`running` と0～100%の進捗を正常に返していた
- 音素時刻は返っておらず、口形は文章から推定していた
- 口モーフだけの更新は14.1ミリ秒だった
- 120ミリ秒周期の全身更新は実モデルで575～621ミリ秒かかっていた
- 画面処理が全身更新に占有され、発話中にUIが反映できた口形は1回だけだった
- VoiSonaの合成処理完了を、音声再生完了だと誤って扱っていた

原因は、利用者のPC性能だけではなく、更新間隔より重い全身計算を画面スレッドで実行する設計と、VoiSonaの状態の意味を誤認した実装です。最初の修正では、0～100%を音声再生位置だと誤認しました。次の修正では、公式チュートリアルの「合成完了後に再生される」という一般説明だけから `succeeded` を再生開始と決め打ちしました。しかし実機では `running` 中に音声が流れ、`succeeded` は音声後に返るため、口パクが音声後に始まりました。利用者の実機結果でこの誤りが確定しました。自動テストが成功していたのは、誤った前提をテスト自身にも書いていたためであり、実際のVoiSona・Windowsバッチ・OpenGLを含む統合動作の成功を意味しませんでした。また、診断用バッチを `cmd.exe` で実行せずに渡したため、Windows用ではない改行による起動失敗まで利用者に確認させました。

このため、状態APIから再生時刻を推測する方式は廃止しました。VoiSona Talk 1.3.7以降のWAV取得機能を使い、アプリ自身が再生したWAVの位置を口パクへ渡します。API状態は「WAVを読み込めるようになったか」の確認だけに使い、再生開始・現在位置・終了の判定には使いません。

さらに、WAVの再生器へ渡したフレーム数を「再生済み」と数える実装にも誤りがありました。Windowsの出力機器は、音が鳴る前に複数のフレームをバッファへ受け取ります。この先送り位置を使うと、口形時刻が会話の途中まで飛び、末尾も音より早く閉じます。現在は音声用Pythonコールバックを外し、Windows標準APIが返す再生済みサンプル位置を使います。回帰テストでは、再生位置がAPIの合成進捗や先送り量に依存しないことを確認します。実際の音声開始との一致は、利用者確認が終わるまで完成扱いにしません。

その後の実機計測で、音声・内部口形は再生位置0秒から正常に進む一方、LLM回答完了時の状態更新が4.454秒間画面を停止させ、その間に音声だけが3.562秒まで進むことを確認しました。原因は、変更されていない98,349面のPMXデータを回答ごとに画面用へ再変換し、GPUへ再転送していたことです。この処理を同一モデルでは再利用する方式へ変更した結果、同じ実画面・同じ処理順の状態更新は0.0ミリ秒、最初の口形は再生位置0.004秒でPMXへ反映されました。以後、通常の状態更新で不変のモデル全体を再構築しないことを回帰テストで固定します。

本プロジェクトでは、次を必須規則とします。

1. 利用者からカクつき、遅延、順序ずれが報告された場合、機能追加より先に各処理時間を測定する
2. 外部APIを含む不具合は、API、内部状態、UI、描画の時刻を一度の診断で記録してから修正する
3. 実測のない開始条件・再生方式・待ち時間の変更を行わない
4. 同じ仮説による修正が一度失敗したら、その仮説を繰り返さず診断へ戻る
5. 自動テスト成功、実機統合成功、利用者確認を明確に区別して報告する
6. バッチなど利用者へ渡す実行物は、正しいWindows改行を含め、実際の起動方法でCodex側が先に確認する
7. Codexが実行できるテストを利用者へ依頼しない。利用者には、音が聞こえるかなど実機でしか判断できない確認だけを依頼する
8. 周期処理は処理時間を測り、周期内に完了しない実装を完成扱いにしない。画面スレッドへ重い全頂点計算を置かない
9. 原因が確定するまで、確認ボタンなど依頼されていない機能を追加しない
10. 修正前に成功条件と中止条件を決め、失敗時は変更点と測定結果を残して同じ作業を繰り返さない
11. 外部APIの合成進捗、再生開始、再生終了を同一視せず、公式仕様と実測で意味を確認する
12. 回答完了や状態表示の更新では、変更されていないPMXモデル全体を再変換・再転送しない
