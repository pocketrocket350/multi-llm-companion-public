# 報告・実機確認手順

プロジェクトの`AGENTS.md`から参照する必須手順。最終報告、実機確認の案内、外部障害による中断時に読み、通常の調査・実装中は毎回読み込まない。

## 説明の前提

利用者はPython、YAML、音声API、MMDの操作経験がないことを前提にする。過去に同じ機能を扱っていても、明示的に簡潔な説明を求められない限り、必要な前提や操作を省略しない。会話が長く続いたことや利用者側の設定を理由に説明量を暗黙に減らさない。

## 完了報告

最終報告は、変更内容、実行したテストと結果、未確認事項、変更ファイル、利用者が次に行う操作の5項目を含める。自動テスト・Codex環境の統合確認・利用者の実機確認を区別する。

実装するかどうかをすべて事前質問する必要はない。安全に判断できる範囲で進め、各項目を次のいずれかに分けて理由を説明する。

- 今回実装した
- 技術的には可能だが、範囲・安全性・実機調整などの理由で今回は見送った
- 現在のAPIや情報では安全に汎用実装できない
- 後続段階へ明示的に計画済み
- 対象外

根拠なく「将来対応」としない。後続段階に含むなら段階番号と予定内容を示し、含まないなら自動的には実装されないと明記する。着手条件が分かる場合は、何を確認できればよいかも示す。

## 実機確認を依頼するとき

先に、対象の表示構成（2D、PMX、画面モード、状態欄の表示・非表示など）で案内する項目が見えることと正確な表示名を、コードまたはCodex環境で確認する。自動テスト・Codex環境で確認したことと、音・見た目・実機APIなど利用者にしか確認できないことを分ける。Codexで実行可能な確認を利用者へ重ねて依頼しない。

単なる確認項目の列挙ではなく、原則として次の7段階を順に説明する。

1. テストの目的
2. テスト前の状態と必要な設定
3. 開くファイル、押すボタン、画面上の位置と表示名
4. 初心者がそのまま実行できる番号付き操作
5. 正常時の表示、聞こえる音、起きる動作
6. 成功条件と失敗条件
7. 失敗時に止める条件、元へ戻す方法、利用者から必要な情報

## 外部障害で中断するとき

同じ失敗操作を反復しない。既に実施したこと、止めた理由、利用者が行う画面上の具体的な操作、成功・失敗時に次に行うことを一度に示す。
