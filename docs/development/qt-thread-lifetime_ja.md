# Qtの終了処理の競合修正（2026-09-29）

## 対象と原因

今回の対象は、画像エラーから普通の会話へ戻る検査などで繰り返し発生していたQtの異常停止。画面・Provider・DB・設定形式・PMX・VMD・音声の選択は変更しない。新しい依存や設定も追加しない。

以前の「1回の全体検査が通った」という理由で原因解消とはしない。今回は既存の画像エラー復帰テストを同一プロセスで反復する小さな再現条件を作り、8回目に未処理のアクセス違反を得た。例外はShiboken（PythonとQtを結ぶ層）のnativeコードで発生し、同時にGUI側は `_worker_finished` でworkerのPython参照を解除していた。GCの同時実行は観測していない。画面更新callbackが別スレッドで走ったという仮説も、今回の実測では裏付けられなかった。

`QThread.finished` はnativeスレッドの終了処理がすべて済んだという通知ではない。旧実装は通知を受けるとQThreadの削除を予約し、worker参照もすぐ解除していた。QObjectの破棄や残った終了処理と競合する余地があった。終了通知の後半を意図的に遅らせる検査でも、修正前は停止、修正後は参照を保持したまま終了処理を完了できることを確認した。

終了完了を待つ修正だけでは、全体検査で本文の幅計算停止が再発した。この停止中の検査プロセスからnativeのスタックを取得し、GUI側は `QTextDocument::setTextWidth → QAbstractSlider::setRange → QMetaObject::activate → QBasicMutex::lockInternal`、作業側は `QObject::~QObject → Sbk_GetPyOverride → PyGILState_Ensure` で待っていることを確認した。GUI側がPythonの実行権（GIL）を保持してQtのロックを待ち、QObjectの接続を解除する作業側がQtのロックを保持してGILを待つ相互待ちだった。本文の描画・選択を削る対応では解決しない。

[Qt公式のQThread説明](https://doc.qt.io/qt-6/qthread.html#isFinished)でも、`finished` 後に後始末が続く場合があり、全処理との同期には `wait()` が必要とされる。[Windowsでのwaitの保証](https://doc.qt.io/qt-6/qthread.html#wait)を利用した。ライブラリを更新する対応ではない。

## 差分

`ui/chat_window.py` の通常会話・能動会話・音声開始・ブラウザ画像取得の4経路を、次の同じ順序にした。

1. 通信や生成を非同期で実行する。
2. 各workerは `finally` でQObjectを作成元のGUIスレッドへ戻し、終了を通知する。
3. GUIで `wait()` によりnativeの終了処理を完了させ、workerとQThreadの削除をGUI側へ予約してから参照を解除する。
4. 操作可能な状態への復帰、保留操作、閉じる処理を進める。

通信中にGUIから結果待ちをする変更ではない。`deleteLater` を作業側で実行する接続を外し、GUI側で破棄する。既存の世代番号と取消、外部送信の許可、画像履歴、出典・本文・音声の分離は維持する。タイマー待ち時間の追加、例外の握り潰し、GCの停止、テストの無効化は行っていない。

同じ寿命の確認で、音声開始中のcloseが受理される経路と、次の発話が未終了の音声workerを上書きする経路もテストで再現した。音声開始中のcloseは古い発話を無効化して終了まで保留し、自動で閉じる。次の音声は前の受付処理と姿勢準備の完了後に開始し、保留中に停止された発話は再開しない。

## 検査と限界

証拠・計画・修正前コピー：`local/diagnostics/qt-stability-20260929/`。

- 修正前：画像エラー復帰の反復8回目で未処理access violation。別の終了遅延テストは停止し、native監視で期限を設けて終了した。通常アプリへはattachしていない。
- 新しい回帰テスト：最終コードで7件成功。4種類のworkerで、終了通知後の参照保持、GUIでのQObject破棄・復帰を確認。音声開始中のclose保留、次の音声の重複防止、保留中の停止も含む。破棄スレッドの条件は修正前4件失敗、音声の境界条件は修正前3件失敗している。
- 中間の関連検査：196件成功。検索・画像のエラー復帰と取消、会話・音声操作、画像ドロップ、会話表示を含む。後続の全体検査による反証を優先し、この結果だけで解消とはしなかった。
- 画像エラー復帰の60回反復：終了wait追加後に60件・正常終了。GUI破棄変更も含む**最終コードでも60件成功（57.35秒）、nativeの未処理例外・時間切れなく正常終了**した。最終検査は受信callbackを置換せず、`stress_final_raw-pytest.log`、`stress_final_raw-native.jsonl` に保存。
- 最初の全体 `test.bat`：本文幅計算で停止。検査プロセスから上記nativeの相互待ちを取得後、検査ツリーだけを終了した。通常権限の終了が拒否された記録と、PID・コマンド確認後の終了成功記録も保存した。
- 最終の全体 `test.bat`：**1,727件成功、286.64秒。Ruff check成功、formatは293ファイルすべて成功**。最初の全体検査の停止原因を追加修正してから実行し、プロセスは正常終了した。`test-bat.log`、`test-bat-result.json` に保存。以前の失敗は `test-bat-initial.log`、`test-bat-initial-result.json` として保持。
- 最終コードの隔離PMX確認：通常DB・YAML・人格・QSettingsを分離し、実際の雨衣PMXで100%／Qt倍率150%を別プロセス実行。各8回の画像エラー→普通の会話、ブラウザ形式の画像プレビュー、履歴・設定開閉、通常1100×760／小画面800×600／最大化、取消後の遅着破棄と会話復帰、worker解放、closeを確認。100%は15.86秒、150%は15.00秒で正常終了した。保存した通常・小画面のスクリーンショットでも表示を確認した。`app-checks-final.json`、`dpi100-final/`、`dpi150-final/` に保存。
- 隔離確認の通信・音声開始はMock／fixture。外部APIは0要求で、実音声・実マイク・実ブラウザ間のマウスドラッグを試したという結果ではない。通常DB・localの設定等8ファイルと通常QSettingsは前後のハッシュが一致した。描画コードやPMX／背景の読込経路は変更していない。

途中の診断失敗も保持する。最初の監視コードはcallbackを同名のwrapperで置き換えて受信に影響し13失敗したため、アプリの結果に数えない。置換をやめた順序診断は602件成功・読み返し位置1件失敗。後の通常の受信経路による関連196件では同じ読み返し位置テストも成功した。修正後の反復検査は最初58回成功時点で診断器の60秒制限に達し、完走として数えなかった。

過去の失敗ログは保持する。今回同じ本文幅計算停止をnativeまで診断できたが、nativeの証拠がない過去のすべての停止まで同一原因だったとは断定しない。実API・実音声・実マイクの成功や、新12の60分会話／8時間待機を今回の短時間確認から主張しない。フェーズ11全体の利用者受入、フェーズ10の残確認も変更しない。

## 利用者の操作

新しい設定は不要。通常のアプリを一度閉じ、いつもの起動方法で開き直す。見た目や会話・添付の操作は同じ。

検査用にAPIエラーを起こしたり、画像を何十回も送ったりする必要はない。普段の会話で返答後も入力できること、必要なときに入力欄上の取消／停止を押してから次の話へ戻れることが正常な状態。再び画面が固まる・突然閉じる場合は追加の送信を止め、発生時刻と直前の操作を知らせる。検査のために通常DBや設定を消さない。

## 変更ファイルと復元

製品コードは `src/multi_llm_companion/ui/chat_window.py`、`ui/workers.py`、`ui/image_attachment.py`。回帰テストは `tests/test_worker_lifetime.py`。文書はロードマップ、フェーズ11利用者手順、本書。

上記証拠フォルダーに `changes.diff`、`changes.json`、`before/`、`restore.py` を保存する。`restore.py` は既定でハッシュ照合のみを行い、アプリ終了後に `--apply` を付けた場合だけ今回分を戻す。後続編集があれば全件を変更せず止める。通常DB・設定・素材を復元対象に含めず、以前の画像・検索の変更も残す。

復元が必要な場合だけ、アプリを閉じ、プロジェクトのフォルダーでPowerShellを開いて次を実行する。通常利用には実行不要。

```powershell
.venv/Scripts/python.exe local/diagnostics/qt-stability-20260929/restore.py --apply
```

`--apply` を付けずに実行すると、変更せず復元可能かだけを確認する。復元は今回のQt修正も取り消すため、元の異常停止の可能性が戻る。
