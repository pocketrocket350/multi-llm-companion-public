# KNO-0001: 音声・口パク同期は実再生時計とUI処理時間で診断する

## 結論

音声合成の進捗、データ受信、再生開始、再生位置、再生終了は別の状態として扱います。口パクとモーションは、状態名や音声バッファへ渡した量から推測せず、可能な限り音声機器の実再生位置へ同期します。

音声だけが先へ進む場合は、音声経路だけでなく、回答完了時のUI処理、PMX変換、GPU転送を同じ時計で測ります。設定周期より重い画面処理は、口パク停止や同期ずれの直接原因になり得ます。

## 適用条件

- 音声の先頭欠落、口パクの遅れ、末尾の早期終了、再生後の口パク開始を調べる場合
- 発話中にPMXやUIが止まる、カクつく、まとめて動く場合
- 外部音声APIの状態名を再生状態として解釈しようとする場合

別の音声APIやOSへ、そのまま状態名や時刻取得方法を一般化しません。それぞれの一次資料と実測が必要です。

## 観測と原因

2026年7月の障害では、次の別々の問題が同じ口パク症状へ重なっていました。

1. VoiSona Talkの合成進捗と完了状態を、音声の再生位置と終了だと誤認していた。
2. 音声バッファへ渡したフレーム数を再生済みと数え、実際の出力より口形時計が先行した。
3. 回答完了時に変更されていないPMX全体を再変換・再転送し、画面処理を数秒停止させていた。

READMEの記録では、120ミリ秒周期の全身更新に575～621ミリ秒かかり、別の実機計測では回答完了時の状態更新が4.454秒間画面を停止しました。不変PMXデータを再利用した後、同じ状態更新は0.0ミリ秒、最初の口形は再生位置0.004秒で反映されました。

## 失敗した方法

- APIの0～100%進捗を、音声の再生位置として扱う。
- 一般的な説明だけから、`succeeded`を再生開始または終了と決める。
- 音声機器へ先送りしたフレーム数を、利用者が既に聞いた位置として扱う。
- 共通時計による経路計測前に、待ち時間や開始条件を変更する。
- 自動テストへ実機と同じ誤った前提を書き、統合成功の根拠にする。
- 回答ごとに変更されていないPMXモデルを再変換・再転送する。

## 安全な経路

1. 合成、データ受信、再生開始、現在位置、再生終了を別々に記録します。
2. 外部API、内部状態、音声機器、UI、PMX描画へ同じ基準時計の時刻を付けます。
3. 設定周期と各処理時間を、修正前の同一条件で測ります。
4. 音声機器が返す実再生位置を同期元にします。
5. 不変のPMXデータを再利用し、重い全頂点計算を画面スレッドへ置きません。
6. 最小修正後に同条件で再計測し、自動テスト、Codex環境の統合確認、利用者の実機確認を分けて判定します。
